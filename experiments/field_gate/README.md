# 实验 4：展开门控的证伪 —— 伤害能否被静态预测？

## 背景

容量展开（实验 1）在多数设计上以少量质量换 30% 量级迭代节省，但在
bigblue3 上灾难性失败——其连通性场坍缩成一个点状致密团，有界密度的
摊开把强连通单元拉散到全版图，长程秩序被破坏。工程上自然的补救是
**门控**：找一个初始化时刻就能算出的廉价统计量，预测"这个设计展开会
受害"，超过阈值就退回不展开的场初始化。

## 动机与方法

（A 部分）候选统计量应当刻画"场有多坍缩、展开有多剧烈"。为 8 个设计
在 CPU 上复现"场 → 展开"流水线（复用运行时同款函数与种子），测量：

- 场跨度（5–95 分位覆盖面积 / 版图面积）；
- 展开位移中位数（相对版图对角线、相对场自身半径两种归一）；
- 展开前后初始 HPWL 膨胀比（吸附前/吸附后两种口径）；
- 场质心、展开态质心、固定引脚质心相对版图中心的偏移。

以实验 2 已有的 obsfield / obsspread 成对结果为"受害/受益"真值标签，
检验哪个统计量能分离受害组 {bigblue3, bigblue4}。

（B 部分）探测中发现坍缩场的展开对随机扰动**混沌**（同族种子下初始
HPWL 可差 2 倍），于是追加判别：伤害是结构性的，还是"切割运气"？
obsspread 在 bigblue3 / bigblue4 / adaptec2 上各加两个种子重跑。

## 实现

`scripts/spread_gate_probe.py`（CPU 探测，逐设计输出统计量矩阵）；
门控旋钮 `conn_spread_hpwl_gate` 完成设计但**在证伪后主动不合入**代码库。
种子批次仅改配置的 `random_seed`，零代码改动。

## 结果

**A 部分（CPU 数据，干净）：没有任何单一统计量能分离受害组。**
三组致命反例：adaptec2 与 bigblue4 场跨度几乎相同（0.0056 / 0.0057）
而结局相反；bigblue3 的展开位移中位数是全场最低，却是唯一灾难；
adaptec2 初始 HPWL 膨胀 6.3 倍却是最大受益者，bigblue3 膨胀 7.8 倍
是灾难。质心类指标同样无区分度（bigblue3 场质心几乎完美居中）。

**B 部分：伤害是结构性的。** 三个种子的最终结果极差仅 0.10–0.41 个
百分点（远小于组间差异），且 overflow 里程碑对齐显示三条种子轨迹从
overflow 0.60 起就重合——混沌的初态被优化器汇入同一质量的盆地族。
里程碑分析同时给出唯一幸存的门控形式：**竞速门**——展开与不展开两个
候选各跑到 overflow ≤ 0.4（约半程），用当时 wHPWL 择优，三个测试设计
上判别边际（≥1.8%）均远超种子噪声；代价是败者的半程运行。

**数据有效性**：A 部分为 CPU 计算不受 conn-y 缺陷影响，但其"受害/受益"
标签、以及 B 部分的 GPU 运行，均基于意外变体。修复后展开的伤害面收窄
（唯一大受害者 bigblue3 +9.27%，实验 R），门控问题的严重性随之下降，
上述证伪结论未在修复后重做——但"静态几何量不预测动力学结局"的模式
与修复后其他观察一致。

## 反思

- **伤害是优化动力学的性质，不是初始几何的性质**——同一结论在本项目
  中反复出现（adaptec4 的历次诊断、种子结构性），这是比门控本身更重要
  的产出。
- 本实验留下了一条已写入项目规范的方法论教训：CPU 探测复现的初始状态
  与真实运行的迭代 0 数值存在约 2 倍差异，当时被"坍缩场混沌 + 随机数
  消耗差异"合理化——事后证明那正是 conn-y 缺陷的直接签名。**探测与
  运行的不一致本身就是缺陷信号，必须追查到逐字节一致才能放行。**
